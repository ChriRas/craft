CRAFT

Coding with Rules · Autonomy · Feedback · Tests

Ein Claude-Code-Plugin, das einen disziplinierten, sprach­unabhängigen Coding-Workflow in wiederverwendbare Slash-Commands und Skills verpackt: ein 9-Phasen-Loop mit explizitem Wissensmanagement, Autonomie-Stufen, Vertical Slicing und Bug-Verifikation — identisch für Shell-Skripte, Libraries, REST-APIs, Full-Stack-Apps und Infrastruktur-Code. A Claude Code plugin that wraps a disciplined, language-agnostic coding workflow into reusable slash commands and skills: a 9-phase loop with explicit knowledge management, autonomy controls, vertical slicing and bug verification — identical across shell scripts, libraries, REST APIs, full-stack apps and infrastructure code. New in CRAFT 2.0: a complete autopilot for whole epics, and interactive slices that move from phase to phase by themselves — every choice a click.

Das Problem & die IdeeThe problem & the idea

Unstrukturiertes Agent-Coding scheitert auf zwei bekannte Arten: Der frei laufende Agent verliert nach wenigen Iterationen die Richtung — er refactort funktionierenden Code, das Kontextfenster gerät in die „Dumb Zone", und die Entscheidungen von gestern sind weg. Das Wasserfall-Gegenteil überplant ein Feature, das noch niemand verstanden hat. CRAFT setzt dazwischen an: gleicher Workflow, gleiche Kontrolloberfläche — egal welcher Stack.

Das Kernprinzip: menschliche Kontrolle konzentriert an den harten Phasen (Planung, Recap, Review, eskalierte Bugs) — die Ausführung wird an sichere, parallele Agent-Arbeit delegiert, oder sie wird im optionalen Autopilot-Modus auf ein Plan-Gate und eine Freigabe am Ende des Epics verengt.

Neu in CRAFT 2.0: Die Zwischenreleases 1.6–1.8 haben Autopilot und Epic-Close Stück für Stück geliefert; 2.0 schließt sie ab und bringt den Rest.

  • Der Autopilot ist vollständig — /craft:execute <epic> --autopilot plant die offenen Einträge eines Epics, fragt dich einmal am Plan-Gate und baut, verifiziert per Befehl, reviewt und committet dann Slice für Slice auf einem Epic-Branch; er hält nur, wo ein Mensch gebraucht wird. Ohne --autopilot ändert sich nichts (Ausführung).
  • Interaktive Slices laufen von selbst — mit ## Slice Flow → Mode: auto (dem Standard) startet jeder Phasen-Command den nächsten, bis einschließlich /craft:commit (Autonomie).
  • Jede Wahl ist ein Klick — Buchstaben-Menüs und Ja/Nein-Fragen kommen in einer interaktiven Session als AskUserQuestion.
  • Ein Pause-Wort — eine Nachricht, die nur pause, pausieren oder /craft:pause lautet, pausiert den Slice am nächsten sicheren Punkt.
  • Fertige Epics schließen sich selbst — /craft:commit schließt ein Epic nach dem Merge eines Autopilot-Laufs, nach einem sequenziellen Lauf oder nach Slice-für-Slice-Arbeit, auch über einen PR unter geschütztem main (Abzweigungen).
  • Worktrees zählen nach ihrer Art — ein Worktree ohne slice-<NNN>- / epic-<NNN>-Branch ändert nicht mehr, was /craft:commit tut, und ein In-place-Slice landet immer auf dem Trunk.

Unstructured agent coding fails in two familiar ways: the free-running agent loses direction after a few iterations — it refactors working code, the context window enters its "dumb zone", and yesterday's decisions are gone. The waterfall opposite over-plans a feature nobody understands yet. CRAFT sits in between: same workflow, same control surface — regardless of stack.

The core principle: human control concentrated at the hard phases (planning, recap, review, escalated bugs) — execution is delegated to safe, parallel agent work, or, in the opt-in autopilot mode, narrowed to one plan gate and an epic-end sign-off.

New in CRAFT 2.0: the interim releases 1.6–1.8 shipped the autopilot and the epic close piece by piece; 2.0 completes them and adds the rest.

  • Autopilot mode is complete — /craft:execute <epic> --autopilot plans an epic's open entries, asks you once at the plan gate, then builds, verifies by command, reviews and commits slice after slice on an epic branch, stopping only where a human is needed. Without --autopilot, nothing changes (execution).
  • Interactive slices flow by themselves — with ## Slice Flow → Mode: auto (the default), each phase command starts the next, up to and including /craft:commit (autonomy).
  • Every choice is a click — lettered menus and yes/no confirmations come as AskUserQuestion clicks in an interactive session.
  • A pause word — a message that is only pause, pausieren or /craft:pause pauses the slice at the next safe point.
  • Finished epics close themselves — /craft:commit closes an epic after an autopilot merge, a sequential run or slice-by-slice work, also through a PR under protected main (branch-offs).
  • Worktrees are judged by kind — a worktree on no slice-<NNN> / epic-<NNN> branch no longer changes what /craft:commit does, and an in-place slice always lands on the trunk.

Vier DisziplinenFour disciplines

Kontext-ResetsContext resets

Jede Phase endet mit einem Markdown-Checkpoint. Chat ist kein Speicher — was zählt, wird noch im selben Zug in eine dauerhafte Datei geschrieben („Durable Capture"). Every phase ends with a Markdown checkpoint. Chat is not storage — anything that matters is written to a durable file in the same turn ("Durable Capture").

Vertical Slicing

Jeder Slice ist Ende-zu-Ende testbar und eigenständig erlebbar — kein „Frontend jetzt, Backend später". Slices sind feature-förmig, nicht komponenten-förmig. Every slice is end-to-end testable and standalone-experienceable — no "frontend now, backend later". Slices are feature-shaped, not component-shaped.

Wissens-SchichtenKnowledge layering

State (Code) ist abgeleitet; Intent (Warum) und Rules (Wie) sind explizit. Der Agent schlägt Änderungen an dauerhaftem Wissen vor — der Mensch bestätigt. State (code) is derived; Intent (why) and Rules (how) are explicit. The agent proposes changes to durable knowledge — the human confirms.

Explizite Autonomie-StufenExplicit autonomy levels

Lesen ist still, Edits im Plan-Scope laufen automatisch weiter, Regel-Änderungen brauchen Bestätigung, Push/Deploy fragt immer. Reads are silent, in-scope edits auto-continue, rule mutations need confirmation, pushes and deploys always ask.

Zwei-Ebenen-Architektur: Das Plugin liefert die universelle Hülle (Workflow + Senior-Developer-Baseline, in jeder Session aktiv). Das Projekt behält seine Sprach-/Framework-Spezialisten lokal (.claude/skills/ und .claude/agents/), lazy geladen — plus optionale Stack-Packs (z. B. stack-php-laravel), die in den code-nahen Phasen automatisch dazugeladen werden.

Two-tier architecture: the plugin ships the universal shell (workflow + Senior-Developer baseline, active in every session). The project keeps its language/framework specialists locally (.claude/skills/ and .claude/agents/), lazy-loaded — plus optional stack-packs (e.g. stack-php-laravel) autoloaded during the code-near phases.

Kontext-Hygiene — der unterschätzte Effizienz-HebelContext hygiene — the underrated efficiency lever

Die Implementierungs-Session eines Slice sollte unter grob 150.000 Tokens bleiben (die Leitlinie für Phase 4). Passt ein Slice nicht in eine Session, war er schon in Phase 3 zu groß — beim nächsten Mal kleiner schneiden. Ist die Grenze erreicht, lohnt ein beherzter Schnitt: /clear — und der SessionStart-Hook stößt /craft:prime automatisch wieder an. Weil aller relevanter Zustand in Dateien lebt (Slice-Plan mit Status-Token, Intent, Rules, Profil), landet die frische Session ohne Verlust exakt an der richtigen Stelle — genau dafür ist das Status-Token-Design gebaut. Regelmäßiges Leeren statt endlosem Weiterschleppen hält das Modell aus seiner „Dumb Zone" und bringt spürbar Effizienz.

Keep a slice's implementation session under roughly 150,000 tokens (the Phase 4 guideline). A slice that does not fit in one session was already too big in Phase 3 — slice smaller next time. Once you reach that mark, a clean cut pays off: /clear — and the SessionStart hook automatically re-triggers /craft:prime. Because all relevant state lives in files (the slice plan with its status token, intent, rules, profile), the fresh session lands exactly where you left off, losing nothing — that is precisely what the status-token design is built for. Clearing regularly instead of dragging context along keeps the model out of its "dumb zone" and is a real efficiency win.

Der zweite Hebel ist die harte Abhängigkeit von context-mode — sie ist kein Zufall: context-mode führt große Ausgaben (Logs, Diffs, Suchläufe, Doku) in einer Sandbox aus und lässt nur die destillierte Antwort ins Kontextfenster. Das spart aktiv enorme Token-Mengen und erlaubt deutlich größere Sessions — erst dadurch läuft der 9-Phasen-Loop eines Slices in einem Rutsch.

The second lever is the hard dependency on context-mode — and it is no accident: context-mode runs large outputs (logs, diffs, searches, docs) in a sandbox and lets only the distilled answer into the context window. That actively saves enormous amounts of tokens and allows much larger sessions — it is what lets a slice's 9-phase loop run in one go.

What the orchestrator guarantees

  • Worktree trust: worktrees live outside the project root (../<repo>-worktrees/<slice-id>-<slug>/). Their base directory is added — once, after confirmation — to permissions.additionalDirectories in .claude/settings.local.json so permission prompts can't stall the run.
  • Lock file: .claude/plans/.execute.lock prevents concurrent runs. It is never removed; its content says held or released, and whether a new run takes it over is execute-lock.sh's fixed rule (the owner is the Claude Code process). Post-assertions verify its release.
  • Dependencies: slices with Depends-On are resolved as a DAG; only the free "frontier" runs in parallel.
  • Epic entries ↔ slice IDs: /craft:plan links a refined decomposition entry to its slice ID. A6 resolves entries only through scripts/epic-entry-link.sh (plan / landed / missing / ambiguous / unlinked) — so a re-run still finds a slice that has already landed. An entry without a slice ID is rejected, even while its plan exists, with the command that links it.
  • Review checkpoints: slices marked in the epic plan halt the run before merging; a shown checkpoint is recorded with the slice's tip in the epic worktree's .craft/checkpoints.md — the next run counts as the go-ahead and merges; a slice changed since it was shown halts again.
  • Re-runs: a second /craft:execute builds on what an earlier run left behind. Step 1c (scripts/execute-resume-state.sh) reads it before any write: worktrees are reused (reuse), merged slices skipped (skip), a sequential epic's stopped slice resumed (resume), paused or blocked slices left where they are (held). Anything nothing accounts for — a leftover branch, a dirty tree, an uncommitted epic plan (plan_not_committed) — aborts before anything is created and names the fix. A slice's plan needs no commit: step 5 copies it into the new worktree (scripts/plan-roundtrip.sh in).
  • Clean tree: CRAFT's own plans, ID counters and local state do not count as uncommitted work (scripts/tree-dirt-state.sh). An epic worktree is created only from a base that holds the epic plan byte-identical; a slice's plan is copied into its worktree instead. Under protected main a tracked plan's removal rides in the approved PR; the second /craft:commit pass drops the local copy before it syncs the trunk (scripts/plan-landing.sh).
  • Autopilot (--autopilot) — the hands-off path: builds an epic, whatever Epic Mode says, slice by slice in place on epic-<NNN>-<slug>, with no halt between slices; main does not move until you say yes at the end. Needs a session started with CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1 claude (foreground builders). A session not on Sonnet gets a one-line cost note — the run never switches the model itself (a0).
  • Autopilot — planning and the plan gate (ap): when active plans exist that no epic entry links while entries are still unplanned, the run asks first — one of them may already plan an entry: [P] plan anyway · [N] stop (link them, or /craft:abort them, first). Then slice-planner agents plan every unplanned entry (the master allocates the IDs and links the entries), a plan-architect reviews the package — its findings go back to the planners up to twice — and the run stops once at the plan gate: the package plus the briefing, [Y] run · [R] <slice-id>[, …] — <note> revise · [N] stop. [Y] is withheld while a plan failed a check, an entry failed, or any NEEDS-HUMAN: line is open; open plan-architect findings do not withhold it. Whether the gate is still owed is derived by scripts/plan-gate-state.sh.
  • Autopilot — run-start briefing (a1): every invocation, re-runs included, relays the block of scripts/autopilot-briefing.sh unchanged: title, branch, that the checkout is occupied, the slice order (topological by Depends-On, ties in decomposition order), "Stops for you at", how to stop and how to resume. If the script fails, the run ends with ⛔ … briefing failed; scripts/autopilot-log.sh refuses every slice step until this invocation's run started is logged.
  • Autopilot — building (a2/a3): a foreground slice-builder per slice, then /craft:commit at Level 2 (split without questions, decisions [K]) on the epic branch. Phase 7 records up to two refactor candidates, applies none and lists them in the epic digest; every event goes to the epic plan's ## Autopilot Log. Phase 5 is checked by scripts/verify-run.sh, by command, from the Test Strategy's <!-- craft:verify --> block (each command judged against your deny / ask rules first); only a clean pass replaces your check, and each slice's landed line records whether Phase 5 was verified by command or by you. A bug (a failed check, or a 2nd fix on the same symptom in Phase 4) first gets an autonomous /craft:debug loop whose attempts verify-run.sh judges. In review, only a Heavy + needs-rethinking finding gets one autonomous loop-back to Phase 4; its reopen (TRIP=reopen:<ID>) or the round cap (TRIP=round-cap) blocks the slice, with an escalation package of at most 15 lines.
  • Autopilot — stops: an exhausted debug loop, a refused or missing check, a tripped ping-pong breaker, a blocker or a failure ends the run (⛔ … stopped:), and so does the budget guard (scripts/usage-state.sh from the statusline tap, limits in the profile's ## Autopilot: no slice the 5-hour window cannot carry with the forecast, a stop at the builder's next boundary — sub-task, phase or debug attempt —, no slice past the weekly limit; without a reading after every slice); a re-run resumes it. The orphan question, the plan gate, the a5 sign-off and every ⛔ stop are answered by typing, not by a click — the cache guard sees a prompt, not a click. Each such stop first says until when the prompt cache is warm; an answer that arrives later, when a re-write would be expensive, is blocked by hooks/cache-guard.sh with the restart.
  • Autopilot — sign-off (a5): at the end a digest generated by scripts/epic-digest.sh (not written by the master from memory) with every slice's UX demo script as written, and the question Merge <epic-branch> into <trunk>? — the run holds its lock until you answer. [Y] under direct: git merge --no-ff <epic-branch> into the trunk. [Y] under pull-request + Protected-main: yes: pushes the epic branch and opens a PR whose body is the digest — run /craft:commit before you approve it: it adds the epic's record to that PR. [N]: complete, not merged, no close. A session that ends unanswered writes nothing and keeps the lock; a re-run asks again.
  • Epic-close: /craft:commit closes a finished epic — its decisions, epic archive, epic plan and, for an autopilot epic, its epic branch: after an autopilot run's merge or PR (KIND=autopilot), after a sequential epic's s5, and for an epic worked slice by slice by hand (KIND=sequential). Whether it is ready is derived by scripts/epic-close-state.sh; it asks [Y] close it / [N] leave it open first. Under protected main it runs in two passes — through the epic's open PR or, when none is open, through a close branch of its own, epic-<NNN>-<slug>-close, and a close PR: the first pass puts the record into the PR, the second merges via gh after your approval and syncs the trunk.
  • Hard limits: never merges into main itself (that is /craft:commit; the one exception is your [Y] at the end of an autopilot run), never resolves Heavy+rethinking findings itself. It pushes only where a PR must be opened — under protected main, an autopilot run's epic branch on [Y], and a sequential epic's slice branch, whose PR /craft:commit opens in s3; never the trunk, never with force. What a stop does depends on the path: in parallel mode one slice's handoff doesn't abort the run — independent slices continue — and an interrupt pauses every slice still running, with its pause record. In an autopilot run a Handoff, Failure or Held stop ends the whole run (⛔ … stopped:) and releases the lock; Esc ends it where it was and pauses nothing — the lock stays held, the re-run's A4 asks whether the earlier run ended ([N]), then the slice resumes. In a sequential epic a mid-slice hard stop releases the lock and stops; the re-run resumes the slice.

Around it: /craft:worktree-status (overview of all worktrees incl. live handoff markers), /craft:checkout (switch into a worktree for inspection), /craft:worktree-clean (remove orphaned worktrees after confirmation, showing an open handoff first — never with --force).
